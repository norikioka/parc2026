週5〜10時間／GPU環境はColab Pro(L4)先行、RunPodは保険（詳細は本文「役割分担」節参照）。

## 【2026-08-04】計算資源は有限であり、実験設計を先に決めてから使う方針

Colab Proのコンピューティングユニットは約30時間分、RunPodは$10（時間換算で20時間弱）と、
残り約10日に対して計算資源は潤沢ではない。加えてリーダーボード提出も1日1回までしか採点されない。
「回してみて結果を見てまた回す」という総当たり的な進め方は割に合わないため、以下を徹底する。

1. **GPUを使わずできる作業（コード実装・設定確認）はローカルで先に済ませる**。ステップ3の
   `MyPolicy`実装・観測変換ロジックなどはColabを使わずローカルで書き、Colab側は動作確認のみに絞る
2. **1回のGPU実行に複数の目的を詰め込まない代わりに、1回で得られる情報を最大化する**。
   例えば学習のやり直しより、既存モデルの評価精度を上げる（`EVAL_EPISODES_PER_TASK`を増やす等）方を優先する
3. **リーダーボード提出は「何を比較するための提出か」を事前に決めてから行う**（対照実験として扱う）

### 提出形式（最重要・旧想定と異なる）
LeRobotの`lerobot-eval`をそのまま提出するのではなく、**HTTPポリシーサーバー一式のzip**を提出する。
`submission_template/policy_server.py`の`MyPolicy`クラスだけを編集し、それ以外（FastAPIサーバー部分・
シリアライゼーション）は変更不可。

```
submission.zip
├── policy_server.py   # MyPolicyクラスを編集(必須)
├── requirements.txt   # 追加依存があれば記載(必須)
└── model_weights/     # チェックポイント等を配置(任意)
```

**観測(observation)の形式**:
- `agentview_image`: (128,128,3) uint8
- `robot0_eye_in_hand_image`: (128,128,3) uint8
- `robot0_joint_pos`: (7,) float
- `robot0_eef_pos`: (3,) float
- `robot0_eef_quat`: (4,) float
- `robot0_gripper_qpos`: (2,) float

**アクション出力**: (7,) float32 相対値 `[dx, dy, dz, droll, dpitch, dyaw, gripper]`

**エンドポイント**: `GET /health`（起動確認）、`POST /reset`（instruction, seedを受け取る）、
`POST /act`（msgpack観測→msgpackアクション）

### タイムアウト制約（超重要）
**`/act`・`/reset` の1リクエストが10秒を超えると、そのTrackはerror扱いで即0点**
（平均でも累積でもなく1回でも超過でアウト）。サーバー起動（モデルロード含む）は既定120秒。
提出前に必ず`validate_submission.py`のスモークテストで確認する。

### 評価環境・採点環境
- 本番の採点環境: **単一のNVIDIA L4 GPU（VRAM 24GB）**、Track評価に1時間以上かかるとタイムアウト
- 開発・検証は配布リポジトリの`setup.sh`で本番と同一環境を再現できる（Python 3.10, git, unzip必要、
  初回10〜20分。Dockerでの再現も可能で既存環境への影響を避けたい場合はこちらを推奨）
- リーダーボード提出は1日1回まで（採点完了時点でカウント消費、10〜20分程度かかる）

### 評価指標・スコア式（`pipeline/total_score.py`より）
成功/衝突判定をゲートとして、重み付け正規化した滑らかさ指標の積でスコアを計算：
```
smooth_metrics = w1*time + w2*jerk + w3*SPARC + w4*trajectory + w5*rotation
Total Score = (1/N) * Σ success_i * (1 - collision_penalty_i) * smooth_metrics_i
```
重み(w1〜w5、合計1)と各指標の正規化式は非公開。予選ではN=1（本選ではTrack毎の総Trial数）。

**成功判定**: タスクのゴール条件を満たし、かつ衝突なし。衝突は「操作対象(BDDLの`:obj_of_interest`)
以外の物体の変位が1mmを超えたら失敗」という明確な基準（対象物を掴んで動かすのは当然OK）。

### タスク
配布されているのはexampleタスク5件のみ（`compe/t1/T1_TASKS.csv`）。
**本番のTrack1採点は非公開の別タスクセットで実施される**（配布キットの試行回数既定は1タスクあたり20）。

### 禁止事項（要注意）
タスク固有のハードコード全般（外部プランナー、有限状態機械、行動テーブル、成功条件/報酬の直接参照、
評価環境専用のif分岐、非公開タスク識別用fingerprinting、モデルを実質使わないfallback policy）、
zip提出物側の禁止（入れ子圧縮・zip bomb・シンボリックリンク・パストラバーサル・難読化ファイル）、
評価中の外部ネットワークアクセス（ポリシーサーバー⇔評価クライアント間の通信のみ許可）。

### 独自学習の要件
公開モデル構造・事前学習済み重み・tokenizerの利用は可だが、**最終的なAction生成に実質的に寄与する
独自学習要素**が必須。認められる例: LoRA/adapter等の学習済みパラメータ、独自学習したAction
head/decoder。認められない例: ファイル形式変換のみ、モデル名変更のみ、プロンプト/推論パラメータ変更のみ。

## 採用モデル: SmolVLA（公式サンプルに準拠、方針転換）

配布リポジトリの`examples/`に用意されている唯一の公式学習例は
**`lerobot/smolvla_libero_plus`をベースにしたSmolVLAのLoRA追加学習**（`examples/smolvla_libero_spatial_lora.ipynb`）。
**Colab無料T4で数時間で完走すると明記**されている軽量モデル。

これまで検討していたPi0.5（LeRobot経由）はモデルロード時にColab無料枠のRAM(12GB)を超過し、
根本原因の特定にCodex CLIの2段階調査を要した上でRunPodへの環境移行が必要だった
（経緯は`docs/env_setup.md`参照）。公式が最初からSmolVLAという軽量モデルを提示している以上、
**Pi0.5にこだわる理由はなく、保守的戦略（予選突破確実優先）としてもSmolVLAへ切り替える**のが妥当。

- ノートブックの学習条件: LIBERO-plus Spatial 10タスク×各5エピソード(計50)、3,000 steps、
  バッチサイズ1（Colab完走優先の最小構成、伸ばす場合はここが出発点）
- 出力はLeRobot形式の重み。これ単体では提出できないため、`MyPolicy`に組み込んでHTTPサーバー化する作業が別途必要
- ノートブック内評価とTrack1本番採点は条件が異なる（観測解像度256×256 vs 128×128、試行数3 vs 非公開20など）ため、
  ノートブックの成功率は本番スコアの目安にはならない

## 改訂ロードマップ

### 【2026-08-04更新】計算資源の方針: Colab先行、RunPodは保険

Pi0.5(約25億パラメータ)からSmolVLA(約4.5億パラメータ、1/5以下)への変更に伴い、旧戦略にあった
「最初からRunPod」を撤回し、**Colab無料枠を先行させる**方針に変更した。

- Pi0.5でのOOM原因は「モデル生成時にCPU上でfloat32実体を構築する非効率な実装」×「25億パラメータの
  大きさ」の掛け算で顕在化した。SmolVLAなら同じ非効率な実装であってもCPU一時消費は約1.8GB程度で
  Colab無料枠(RAM12GB)に余裕で収まる計算になる
- SmolVLA LoRA学習は公式が「Colab無料T4で数時間の完走」を明言している（`examples/README.md`）
- ステップ1(環境構築・疎通確認)自体も学習を伴わない軽量な作業のため、まずColabで試す
- RunPod(RTX3090等)は、Colab無料枠で解決しないエラーが出た場合・評価パイプラインがT4で重すぎる場合・
  本番環境(L4 GPU)により近い環境で最終検証したい場合の**保険**として温存する
- トレードオフ: RunPodでは直接SSHで実行できたが、Colabでは「ユーザーがセルを実行→出力を共有」という
  往復作業に戻る。SmolVLAは大きなトラブルが起きにくいと見込んでいるが、詰まった場合はこの往復が発生しうる

### 【2026-08-05更新】方針は維持: Colab主戦場・RunPodは条件付きの保険

2026-08-05に「Colabのランタイム切断で環境が毎回消える」「エラーが繰り返し起きる」という問題が
実際に発生し、一時RunPod全面移行を検討したが、根本原因は次の2点であり、**Colabという場所自体の
問題ではなかった**ため、方針そのものは変更しなかった：
1. `setup.sh`実行セルが`rm -rf venv`を無条件実行するよう(意図せず)退行しており、同一セッション内の
   再実行のたびにフル再構築していた → 条件付き削除に修正済み
2. `MPLBACKEND`環境変数を個別セルにだけ設定しており、他のセルで同じエラーが再発していた →
   セクション0.5でPythonカーネル起点に一元化して修正済み

**RunPodを使う条件（すべて満たした時のみ）**: ①提出が2回連続で環境起因のエラーで落ち、
②Colab・ローカルPython 3.10 venvのどちらでも再現しない(本番固有の差分が原因と強く疑われる)、
③8/11以前である。使う場合は**予算上限$4・1セッション最大3時間**、目的を「requirements.txtが
入るか」「オフラインでサーバーが起動するか」の2点に絞り、評価パイプライン自体は回さない。
（詳細な経緯は`docs/env_setup.md`、根本原因分析は本ファイル末尾の教訓セクション参照）

### ステップ3: `MyPolicy`への組み込み・提出物作成

**2026-08-04: ローカルで実装済み**（`src/parc2026/my_policy_smolvla.py` + `libero_obs_processing.py`）。
GPUを使わずに済む部分（観測変換ロジック）はローカルで実装・ユニットテストまで完了させ、
Colab側では「貼り付けて動かすだけ」の状態にしてからGPU実行時間を使う、という方針で進めた。

**実装のポイント（LeRobot公式ソースコードを直接確認して検証済み）**:
- PARC2026の生観測（robosuite形式）→SmolVLA入力への変換は、LeRobot公式の
  `LiberoProcessorStep`（[env_processor.py](https://github.com/huggingface/lerobot/blob/main/src/lerobot/processor/env_processor.py)）
  と同一のロジックを自前実装する必要があると判明。理由: モデル自身が持つpreprocessor
  （`policy_preprocessor.json`）はrename/tokenize/正規化のみを行い、LIBERO固有の変換
  （状態ベクトル構築・画像flip）は含まれていない
- 状態ベクトル(8次元) = `[eef_pos(3), eef_quatをaxis-angle変換(3), gripper_qpos(2)]`。
  クォータニオン→軸角度変換のアルゴリズムも公式実装を再現し、既知の回転角でユニットテスト済み
- 画像はH・W両方向にflip（180度回転）が必須（LeRobotの学習データセットのカメラ向き規約に合わせるため）。
  一方でリサイズは不要（`SmolVLAPolicy.prepare_images()`が内部で自動リサイズ・パディングするため）
- `policy.select_action()`はaction chunk(50ステップ)を内部キャッシュするため、50回に1回だけ
  実際の推論が走る計算になり、10秒/リクエスト制約に対して有利
- `src/parc2026/libero_obs_processing.py`の変換関数（クォータニオン変換・画像flip）はGPU不要なので
  ローカルでユニットテスト済み（9件全てpass）。`my_policy_smolvla.py`本体（LeRobotのAPI呼び出し部分）は
  ローカルにlerobotが入っていないため未検証で、**Colabでの実機確認が必要**

**残作業**: Colab上で`submission_template/policy_server.py`の`MyPolicy`に貼り付けて動作確認、
10秒タイムアウト内に収まる推論速度を確認、`validate_submission.py`で静的検査＋起動スモークテスト。

### ステップ4: ロバスト性対策（余力があれば、2026-08-04調査で優先順位を具体化）

本番タスクは非公開のため、過度なチューニングより「まず確実に動いて提出できる」ことを優先する。
その上で余力があれば、以下を**優先度順に1〜2個だけ**選んで実装する（欲張らない）。

1. **【最優先】カメラ視点・ロボット初期姿勢への耐性強化**: LIBERO-Plus論文自身が
   「カメラ視点・ロボット初期姿勢の摂動で成功率が95%→30%未満に急落する一方、言語指示の
   バリエーションにはほぼ無反応（言語をほぼ無視して視覚パターンマッチングで動いている）」と
   明言している。言語指示のパラフレーズ対策より、**視点・姿勢変化に強くするaugmentation
   （画像の切り出し位置ランダム化・軽い回転/シフト等）を優先する**のが費用対効果最大
2. **【次点・時間があれば】StableVLA型の軽量アダプタ**（[arXiv:2605.18287](https://arxiv.org/abs/2605.18287)）:
   追加10M未満パラメータのInformation Bottleneck Adapterで視覚ノイズをフィルタし、
   追加データなしで平均30%のロバスト性改善を報告。SmolVLAのLoRAと並行して追加できる可能性があり、
   データ拡張なしで効く点が実装コストの低さにつながる。ただし2026-08-04時点で実装未着手・検証もこれから
3. **見送り（コスト対効果が合わないと判断）**: XS-VLA（蒸留による性能改善、実装コスト大）、
   PAIR-VLA（RL後段学習が前提で工数大）。着手する場合も締切までの残り時間と要相談

## 類似コンペ・技術記事の調査結果（2026-08-04）

- **類似コンペは実質「該当なし」**: Kaggle・SIGNATE・Devpost等でLIBERO/VLA/ロボット模倣学習を扱う
  コンペは確認できず。CoRL/ICRA/NeurIPS併設チャレンジでもLIBERO-Plusを直接使ったものは未確認。
  → PARC2026は先行事例の乏しい独自性の高いコンペであり、「上位解法を借りる」ショートカットは
  期待できない。地道な検証（本ロードマップ）が唯一のルートという前提を再確認
- **実務的に役立つ発見**: Zenn記事[「LIBERO標準ベンチマークでπ0/π0.5を再現してみた」(inrjin氏)](https://zenn.dev/inrjin/articles/437a359e3ffcd7)。
  ヘッドレスGPUレンダリング(EGL)はドライバとGLライブラリのバージョン完全一致が必須、
  `~/.libero/config.yaml`未生成だとimport時に対話式質問でEOFエラーになる、推論サーバ(JAX等)の
  メモリ先取りとレンダリングのメモリ競合がOOMの原因になりうる（`MEM_FRACTION`調整で解決）という
  実践知見あり。現行の`setup.sh`は`~/.libero/config.yaml`を自動生成するため一部は解消済みだが、
  Colab上で同種のエラーが出た場合はこの記事のチェックリストを参照する

### （時間に余裕があれば）ステップ6: 新しいモデルの並行実験

**2026-08-04: TurboVLA（[arXiv:2607.27205](https://arxiv.org/abs/2607.27205)）を候補として検討・保留**。
0.2Bパラメータ・無印LIBERO成功率97.7%・推論31.2ms・[GitHub](https://github.com/H-EmbodVis/TurboVLA)で
チェックポイント/評価スクリプト公開済み(Apache-2.0, star306)と、数字上は魅力的。

ただし2026-08-04時点で**主軸への採用は見送り**。理由:
- 投稿5日の未査読プレプリントで、LIBERO-Plus(本コンペが使うロバスト性評価)での数値が一切ない
- PARC2026の`policy_server.py`インターフェースへの組み込み実績がゼロ(SmolVLAは公式サンプルあり)
- 締切まで残り10日程度の段階でモデル切り替えは統合リスクが高い(Pi0.5切り替え時の教訓)

**方針**: ステップ1〜5でSmolVLAによる提出ラインを先に確保してから、余力があれば
TurboVLAを別ブランチ/別ディレクトリでの並行実験として試す。動作すればSmolVLA版と比較し、
明確に優れていれば差し替えを検討する（ただし提出物は必ず動くものを残した状態で進める）。

### 予選参考スコアとの比較（criticレビューMAJOR#7で判明、strategy.mdに見落としていた重要情報）

公式配布物（PDF p.9）に「配布学習例で学習したモデルのリーダーボード参考スコア：Track1＝**0.0633**」
という記載があった。初回PDF読了時（2026-08-03）に見つけていたにもかかわらず、strategy.mdに
一度も反映していなかった。予選は絶対スコアではなく**相対順位（上位200人）**で通過が決まるため、
「動くものが作れたか」だけでなく「この参考値0.0633との比較でどの位置にいるか」を意思決定材料にする。

- 初回リーダーボード提出後、自分のスコアと0.0633を比較する
- 上回っていれば、公式サンプルより上乗せできている証拠として自信を持ってステップ4に進む
- 下回っていれば、ステップ3の実装に問題が残っている可能性が高いと判断し、
  ロバスト性対策より先に基本動作の見直しを優先する

**【2026-08-04追記】ローカルTrack1テストの初回結果と原因切り分け**: `python -m pipeline`での
疎通テスト（compe/t1のexampleタスク4件、各2エピソード）はクラッシュなく完走したが、全タスク
成功率0%だった。criticレビューで最有力容疑とされた「front/wristカメラキー対応の逆転」を
`lerobot/libero_plus`データセットからの実データ目視確認で検証した結果、**対応は正しいと確認**
（front=俯瞰視点、wrist=手先アップの画像を確認、コードのバグではない）。
→ 0%の原因は、LoRA学習タスク(LIBERO-plus Spatial 10種のみ)とTrack1 exampleタスク
(Object/Goalスイート含む、L2〜L5の高難易度摂動)の**分布の違いによる汎化不足**である可能性が高い、
という仮説に更新。

**【2026-08-04さらに追記・plannerへの計画委譲で判明した重大発見】** 誤った提出物（モデル重みのみの
zip）でOmnicampus実採点が`struct.no_policy_server`エラーでFAILし、今日の提出1回を消費した可能性が
高いインシデントが発生。ユーザーから「今日は急いで再提出せず、次の貴重な1回の質を上げる」方針が
示されたため、`planner`に次の提出までの作業計画を委譲した。その結果、8試行(4タスク×2エピソード)の
0%という結果は**統計的に何も証明しない**（真の成功率15%でも8連続失敗する確率は約27%）ことに加えて、
それとは独立に**実ソースコード検証で確定した、より根本的な問題**が見つかった:

- `SmolVLAPolicy`はVLM(SmolVLM2)のトークナイザ・configをHugging Face Hub上の文字列参照から
  ロードする実装になっており（`load_vlm_weights=False`でも`AutoProcessor`側は無条件でHubを叩く、
  LeRobot実ソース`smolvlm_with_expert.py`で確認済み）、**評価中の外部ネットワークアクセス禁止規定と
  真正面から衝突する**。ローカルColabでの成功は学習時に温まったキャッシュのおかげに過ぎず、
  この構成のテストでは原理的にこの問題を検出できない
- モデル本体の重みは`model.safetensors`に既に完全に含まれている（500テンソル中490個が
  `vlm_with_expert.*`）ため、Hubから本当に必要なのは軽量なconfig/tokenizerファイル(計約4.8MB)のみ。
  これを`src/parc2026/vlm_assets/`としてリポジトリにダウンロード・同梱し、`vlm_model_name`を
  ローカルパスに向けることで解決した
- 併せて`n_action_steps`を50→10に変更（chunk_sizeとは独立で安全と実ソース確認済み）。
  600ステップ中12回しか画像を見ない開ループ状態を解消し、LIBERO-Plus型の摂動タスクへの
  追従性を上げる、コストほぼゼロの改善

**結論**: 「0%の原因はタスク分布のズレ」という仮説は依然として否定されていないが、その前に
「そもそも採点環境でサーバーが起動すらしていない可能性」というより優先度の高い問題が見つかった。
次の提出前に、この2点を修正した上でオフライン起動テスト（ネットワーク遮断を再現）を行い、
確実に起動することを確認してから提出する。

## ローカル⇔Colab(Pro)⇔RunPod⇔Codex CLIの役割分担

**【2026-08-04更新】Colab Proへのアップグレードを決定**（月額約1,100円）。
理由: セッション切断（アイドル90分程度で切れる無料枠の制約）が今日の作業でも支障になっており、
Pro化でバックグラウンド実行・長時間セッション・優先GPU割当・ノートブック内蔵Geminiの強化が受けられる。
ただしProでも**本番採点環境と同じL4 GPUが確実に割り当てられる保証はない**ため、RunPodの役割は残す。

- **ローカル(Mac)**: コード編集・構造化・git管理。MuJoCoのGPU描画非対応のため実行環境としては使わない
- **Colab Pro（メイン）**: 配布リポジトリの`setup.sh`実行・`pipeline`での評価・ポリシーサーバー動作確認・
  SmolVLA LoRA学習ノートブック実行。日常的な開発はここで完結させる。
  **Colab ProではランタイムでNVIDIA L4を選択可能（2026-08-04確認）。本番採点環境と同一GPUのため、
  RunPodの主目的だった「本番同一GPUの確保」がColab側で満たせるようになった**
- **RunPod（保険）**: それでもColab(Pro)で解決しないエラーが出た場合の保険として温存する
- **Codex CLI**: 実装のセカンドオピニオンや、Claude Codeと並行させたい作業がある場合に使う

### 【2026-08-05追記】ローカルMacでの新しい検証手段(GPU不要・無料)

MuJoCoのGPU描画自体はローカルでは検証できないが、**「モデルロード・依存解決・ネットワーク遮断下の
起動確認」はColabを待たずローカルMacで検証できる**ことが今日わかった。

```bash
# 特定バージョンのパッケージを一時環境にインストールして試す(既存プロジェクトを汚さない)
uv run --no-project --python 3.10 --with "lerobot[smolvla]==0.6.0" python script.py

# ネットワーク遮断を再現する(実際に外部アクセスせず、HF Hub関連のコードだけを検証)
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 HF_HOME=/tmp/empty_cache python policy_server.py
```

今日はこの手法で、Colab実機を1回も使わずに重大バグ2件（VLM Hub参照の二重ハードコード、
lerobot 0.6.0のPython 3.10非対応）を発見・修正できた。**GPUを使う前に「これはローカルの
Python 3.10 venvで再現できないか」を先に自問する**運用を今後標準にする。

## 【2026-08-05】今日の教訓の制度化

1. **本番との差分表を作る**: 開発環境と採点環境が異なりうる軸（Pythonバージョン／ネットワーク遮断／
   torchビルド／venv種別／GPU／作業ディレクトリ／環境変数／HFキャッシュの温度）を意識し、
   バグを1件見つけるたびに`docs/env_setup.md`のつまずきポイント表に追記する
2. **grepで安全を主張しない、importで主張する**: 構文チェック(`ast.parse`)で検出できるのは
   構文エラーだけ。`typing.Self`/`typing.Unpack`のような「構文は合法だがモジュールに無い」問題は
   実際にimportして初めて見つかる。「N個直したから大丈夫」ではなく「実際に走らせて落ちなかった」を
   根拠にする
3. **1箇所直したら、同じ設定が他にないか全文検索する**: `vlm_model_name`だけでなく
   `tokenizer_processor`にも同じHub参照があった件、`MPLBACKEND`を個別セルに書き足して再発した件は
   どちらも同じ失敗パターン。同じ症状が2箇所で出たら、継承元を1箇所直せないかを先に疑う
4. **エラー対応で安易に`rm -rf`を書き足さない**: 「壊れている」の判定は`activate`の有無など
   機械的な基準にする。対症療法の`rm -rf`が無関係な修正のコミットに紛れて無条件実行に退行した実例が
   今日発生した（`docs/env_setup.md`参照）
5. **新しいライブラリを使う前に`requires-python`を機械的に確認する**: `pip index versions <pkg>`や
   PyPI JSON APIで、使いたいバージョンが対象Pythonに対応しているか事前に確認する一手間を惜しまない
6. **重要な設計判断はplanner/criticに委譲する**: 今回のlerobotベンダリング方針は、
   `planner`によるロードマップ再設計と`critic`(Opus)による2段階レビューを経て実装した。
   締切あり・本番投入・手戻りコスト大のいずれかに該当する判断は自己判断で進めない
